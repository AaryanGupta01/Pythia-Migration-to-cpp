1PYTHIA in 60 seconds

PYTHIA speeds up the slow parts of your Python project, and it proves, using your own program's calls, that the fast version gives the same answers as the original.

The problem

Python is easy to write and slow to run. Loops that add numbers, compare strings or fill tables can be 10 to 100 times slower than the same loop in C++.

People fix this in four ways: rewrite the code in C++, learn a special dialect (Cython), use a JIT (Numba, PyPy), or ask ChatGPT to translate it. Every one of these either costs a second codebase or gives you no evidence that the fast version behaves like the old one.

What we built

Two things, one inside the other.

  • PYTHIA, the compiler. It reads a typed subset of Python (we call it PySub) and writes readable C++17. This is what you built in Reviews 1 and 2.
  • PYTHIA Studio, the app. You give it a snippet, a file, a folder or a GitHub link. It finds the slow functions, works out their types, converts them, compiles them, checks them against real Python, and swaps them in. You see every step and every diff.

What is special

Verified

Each converted function is run against CPython on the calls your program really made. Different answer? It is thrown away automatically.

Fidelity Report

A list of every spot where Python and C++ could behave differently, with the line number and what we did about it.

Whole project

Point it at a repo. It scans, ranks, converts what it can, and tells you in plain English why it left the rest.

No LLM needed

Types are worked out by our own code. Same input, same output, free, works offline.

Readable

The C++ is something a person can open and read. The app shows it next to your Python.

Say itOne-line pitch. “PYTHIA is a compiler plus an app that makes the slow parts of a Python project faster, and proves on your own program’s calls that the fast version is correct.”

The 60-second version, out loud

Python is slow on loop-heavy code. The usual fixes cost you a rewrite, or they ask you to trust a black box. PYTHIA takes an ordinary Python project, runs it once to see where the time goes, converts the hot functions to C++17 using our own type inference, and then replays the function’s real calls through both versions. If even one answer differs, the conversion is rejected. What survives is spliced in behind a one-line decorator, so the original code is still there. On our benchmark kernels the C++ is a median of 11 times faster, and every output matches CPython. It is a compiler, so we built every phase: lexer, parser, type checker, lowering, optimiser and emitter. Where Python and C++ can differ, PYTHIA says so, line by line.

2The whole flow, one function at a time

We follow one real function, collatz_sequence_len from dayyass/project-euler, through every stage. Everything below is real output from the app, not a mock-up.

1 Your Python function

This is the function exactly as it sits in solutions/utils.py. It has type annotations or not; PYTHIA does not care yet.

Why: Everything starts from your own code. Nothing is rewritten by hand.

def collatz_sequence_len(n: int) -> int:
    """
    Compute len of Collatz sequence.

    - O(1) space-complexity
    """
    result = 1
    while n != 1:
        if n % 2 == 0:
            n //= 2
        else:
            n = 3 * n + 1
        result += 1
    return result

4 Tokens: the words of the program

The lexer cuts the text into tokens (keywords, names, numbers, operators). Python uses indentation, so the lexer also invents INDENT and DEDENT tokens where the block gets deeper or shallower.

Why: After this, the parser does not need to count spaces: blocks look like braces.

5 AST: the shape of the program

The parser builds a tree: a function contains statements, a loop contains a body, an expression contains operands. Every node remembers its line and column.

6 Type checking: every node gets a type

The type checker walks the tree and writes a type on each node. It pushes expected types inward (bidirectional) and widens bool to int to float where needed. Any mismatch stops here with a line and column.

Why: C++ needs to know the exact type of everything; this is where we find out.

7 Lowering: make hidden things explicit (PIR)

Python converts silently (an int becomes a float in a / b); C++ must be told. Lowering inserts explicit conversion nodes (none in this function) and attaches a fidelity note to every place where C++ could behave differently. This function has 7 notes.

Why: This is the Semantic Fidelity Report being born.

10:13 D2 floor-division rounding direction (exact)

8 Guard elision: remove checks that cannot fire

Each integer + - * could overflow 64 bits, so by default it is a checked call. The interval analysis proves some cannot: here 0 checks were removed and 2 kept.

Why: Fewer checks, faster code, and never a removed check that was needed.

9 C++17 code generation

The emitter walks the typed tree and writes readable C++17: typed variables, loops, calls into our runtime for Python behaviour.

Why: Readable output means you can review and export it.

10 The pybind11 bridge

A small generated wrapper turns Python arguments into C++ values, calls the function, and turns the result back. Mutated lists are written back. Anything it cannot represent faithfully raises FallbackError, and the original Python runs.

Why: This is the boundary, and it costs time, which is why the ranker predicts it.

static py::object w_collatz_sequence_len(py::object a_n) {

        pyb::raise(_e);

    return pyb::steal(TR::out(_r));
}

The recorded calls are run through both the original function and the compiled one: 500 of 500 calls matched (return value, exception, changed arguments; floats bit for bit). Source of inputs: trace.

13 Benchmark

Python took 0.855 ms per call and C++ 0.040 ms: 21.3x faster (median over repeats). Anything under 1.1x is declined.

Why: A function that compiles is not always worth compiling.

PYTHIA adds a decorator above the original function in the working copy. The body is untouched, so the change is tiny and reversible; if the compiled module is missing, Python runs.

3What changed since Review 2, and why

At Review 2 you could type a PySub program and get C++ out. It worked: 17 valid programs matched CPython, 20 invalid ones were rejected, and we had added the dictionary and set libraries and moved from C11 to C++17.

But think about who would use that. Nobody has a PySub program. They have a Python project that is a bit slow. So we asked: what would a real developer need?

  1. Find the slow parts. Run the program once under a tracer and rank functions by time. (Trace and Rank stages.)
  2. Work out the types. Real code has no annotations, so we infer them ourselves from what the tracer saw and from how values are used. (Fix stage.)
  3. Prove it still works. Replay the real calls through both versions and compare. (Verify stage.)
  4. Put it back without breaking anything. Add one decorator line and keep the original function; if the fast version cannot run, Python runs. (Splice stage.)
  5. Show everything. A desktop app that displays each stage, the diff and the fidelity notes, installable with one click.
Figure 3.1. Review 2 (top) and Review 3 (bottom). “Reused” means the compiler core carried over; everything marked “new” is Review 3 work.
Be readyWe dropped the WebAssembly back end. It was promised for Review 3. A second back end would show retargetability but would not help a developer speed up a Python project, and the time went into the Studio pipeline. Say this first, before they ask. Also say: the compiler’s IR is language-agnostic after the front end, so adding it later is an addition, not a rewrite.

Other targets that moved: the positive oracle corpus is 78, not 120 (we added an independent 91-program gate, snippets and a generator instead); memory is reclaimed per call in library mode but standalone binaries still never free memory.

7Limitations and comebacks

Say the honest answer first, then the comeback. A panel trusts you more if you name the limit before they do.

“What about NumPy, pandas, PyTorch, OpenCV?”

Honest answerPYTHIA cannot transpile functions that call those libraries. The scanner marks them “not eligible” and says why.
Confident comebackThose libraries are already C and C++ inside, so the maths is not where Python is slow. The time goes in the pure-Python code around them. PYTHIA compiles that glue and leaves the library calls in Python. Next steps: call the libraries from compiled code through the CPython C-API, map a NumPy subset onto Eigen or xtensor, or use LibTorch’s C++ API directly instead of transpiling.

“What if the code is dynamic: eval, monkey-patching, a variable that changes type?”

Honest answerThose are rejected with a reason, not guessed at. Our own snippet coin_change is refused because it returns an int on one path and a float on another.
Confident comebackRefusing is the safe answer: the old version of the converter widened it to float and printed 3.0 -1.0 where Python prints 3 -1, and we caught that. To cover more, compile one specialised version per observed type signature, or use std::variant for union types.

“Python ints are unbounded. What happens on overflow?”

Honest answerCompiled code uses 64-bit ints. Operations that might overflow are checked and raise OverflowError; an int beyond 64 bits passed into a compiled function also raises it. We measured both (2**62 * 2 raises OverflowError).
Confident comebackIt fails loudly instead of silently wrapping, and the fidelity report lists every site (class D1). The remedy is bignum promotion on overflow: fall back to an arbitrary-precision type only when a check fires.

“Strings and Unicode?”

Honest answerCompiled strings are ASCII bytes. A non-ASCII argument makes the wrapper raise FallbackError, and the original Python function runs instead, so nothing breaks, you just do not get the speedup.
Confident comebackIt is a safe fallback by design. The fix is UTF-8-aware strings with code-point indexing, which is a runtime change, not a compiler redesign.

“Memory: does it leak?”

Honest answerStandalone binaries never free memory (class D7). In library mode, which is what Studio uses, everything allocated during a call is freed when the call ends. We checked: memory did not grow over 200000 calls (28640 KB before, 28640 KB after), and the repo’s own check shows no growth over 3,000 calls.
Confident comebackSo the Studio path is safe. For standalone programs the next step is a region allocator or reference counting.

“Isn’t crossing between Python and C++ expensive?”

Honest answerYes. Arguments are copied in and out. For a trivial function the call costs about 0.15 µs against 0.038 µs for Python’s own len, and a 100,000-element list costs about 1.18 ms per call to copy.
Confident comebackThat is exactly why the ranker exists: it predicts marshalling cost, and a function whose measured speedup is under 1.1x is “declined” and never spliced. Remedies: zero-copy buffers, keep data on the C++ side across calls, fuse neighbouring hot functions.

“Testing is not proof.”

Honest answerCorrect. Verification is differential testing on recorded and generated calls. It shows agreement on those calls, not on all inputs. Untraced code paths are untested, which is why the entry command matters.
Confident comebackIt is evidence about your program, which a generic proof would not give, and anything that disagrees is rejected. Stronger forms exist and are future work: translation validation per pass, property-based fuzzing around the recorded inputs, and formally proving one pass in the style of CompCert.

“Only Python?”

Honest answerYes: Python in, C++ out.
Confident comebackEverything after the front end works on the typed tree and the IR, which do not know about Python syntax. A new front end is the only addition needed for another source language; a new emitter would give another target.

“Are dictionaries fast?”

Honest answerNo. Our benchmark with a string-keyed dictionary and about 2,000 keys ran about 29 times slower than CPython. The cause is in runtime/pyrt.cpp line 131: the specialised dictionaries scan a vector for every lookup.
Confident comebackCorrect and slow is a fixable kind of wrong: a hash index in that one macro removes it, and the ranker would already decline such a function when the measured speedup is below 1.1x, so Studio would not splice it.

“Generators, threads, files, regex, random?”

Honest answerNot supported: generators are rejected, and I/O, threads, regex and unseeded randomness are refused with a reason (explain.py).
Confident comebackMost hot numeric code does not need them. Seeded randomness is the one we would add first, because a generator with a known algorithm can be reproduced exactly.

“It takes a long time to compile.”

Honest answerThe first build of a module is slow: 15.05 s cold in our library check, 5.63 s for a new module with the runtime already built, and 27 ms when the build cache hits. A whole cold project run takes minutes (Section 10.4 of the report).
Confident comebackBuilds are content-addressed, so a second run of the same project is fast, and the demo ships prebuilt modules. The bundled compiler means nothing is installed.

8The value this adds

Who would use it

  • A developer with a slow Python project who wants the hot functions faster without a rewrite, and wants to review the change as a diff.
  • A team that must justify a port. The Fidelity Report is an audit trail: here is every place the behaviour could differ, and what we did.
  • Students and teachers of compilers. Every phase is small enough to read and the app shows each one.

What it saves

The time to find the hot spots (the tracer does it), the time to hand-annotate (the inference does it), the time to write bindings (pybind11 glue is generated), and the time to convince yourself the fast version is right (replay does it). On the bundled TextLab demo a whole program went from 17.2 s to 6.5 s with no source edits beyond decorator lines.

Why verified matters more than raw speed

A fast wrong answer is worse than a slow right one. Tools that translate quietly change behaviour (a 64-bit integer, a different rounding rule), and the problem shows up months later. PYTHIA’s promise is smaller and checkable: whatever it splices in agreed with CPython on the calls we replayed, and anything doubtful is reported or refused.

Where it could go

  • A research paper on the divergence report as a first-class output of a source-to-source compiler, paired with replay verification. It needs a bigger independent corpus and a comparison with Cython, mypyc and Codon on the same programs.
  • A VS Code extension that shows the gutter and diff inside the editor.
  • CI integration that fails a build when a converted function stops matching.
  • Bignum promotion, UTF-8 strings, zero-copy buffers, type-specialised versions (Section 7).

9Likely viva questions, with short answers

30 questions. Learn the shape of each answer, not the words. Numbers are from this session’s runs (report, Appendix F).

1Isn’t this just Cython?
No. Cython needs you to write C type declarations (or pure-Python mode annotations) and gives you a C extension with Python semantics; it does not check the result against CPython or tell you where behaviour differs. PYTHIA takes untyped code, works out the types, produces readable C++17, and checks every conversion on real calls. Cython is more complete: it handles arbitrary Python and C libraries, and we say so.
2Why not just ask ChatGPT to convert it?
We tried an LLM first (commit dfe6942). Three problems: the free tier ran out (about 200,000 tokens a day), answers change between runs, and nothing proves the answer is right. PYTHIA’s in-house inference is deterministic and free, and everything it produces is checked. An optional LLM fallback still exists, but its output has to pass the type checker and the replay like anything else.
3How do you know the C++ is correct?
Two checks. The oracle compiles 78 programs and compares output and exception class with CPython byte for byte, and rejects 88 invalid programs with the right message. In Studio, every converted function is replayed on at least 50 calls (recorded, topped up with generated ones, and labelled) and the return value, exception and mutated arguments must match; floats are compared bit for bit. It is differential testing, not a proof, and we say so.
4Why are the speedups different from Review 1?
Review 1 reported a median of 9.4x (range 3.3x to 13.8x) on 14 programs with generated C11. The oracle now reports a median of 15.2x (range 6.1x to 46.9x) on 78 programs with C++17 and -O2 -flto. We did not isolate each cause: the backend changed, more programs are in the set, guard elision exists, and those timings are single runs of whole processes. For performance claims we use a separate benchmark: ten fixed kernels, medians of 5 runs, median 11x.
5What happens if someone passes NumPy code?
Functions that use NumPy are marked not eligible, with the reason “uses numpy (a C-extension library)”, and keep running in Python. NumPy’s own loops are already native, so the time is usually in the Python around them, which PYTHIA can compile.
6What did you personally build?
Answer from Section 4 and 5: name your files, the hardest problem, and one function to open. If it is Studio work, say which part you understood and wrote or reviewed, and be straight that AI coding assistants were used and are credited in the repository history.
7Why C++ and not LLVM?
Readable output, and pybind11 needs C++. g++ already optimises well, and we can bundle it on Windows. LLVM IR would not be readable and would need LLVM at run time. The cost: we depend on a C++ compiler, which we ship in the installer.
8What happens on integer overflow?
Checked arithmetic raises OverflowError instead of wrapping (class D1). Where interval analysis proves a result stays within plus or minus 262, the check is removed. An int beyond 64 bits passed into compiled code also raises. Python would have kept going with a big integer, so this is a documented divergence.
9Why did you drop the WebAssembly backend?
It was promised at Review 2. A second back end shows retargetability but does not help a developer speed up a Python project, and the time went to the Studio pipeline. The IR does not depend on Python syntax, so adding it later is an addition.
10What’s a DEDENT token?
Python marks blocks by indentation. When a line is indented less than the previous one, the lexer emits one DEDENT for each block that just ended, so the parser can treat blocks like braces. INDENT is the opposite. The lexer keeps a stack of indentation widths to know how many to emit.
11Explain bidirectional type checking.
Two modes. Synthesis works a type out from the expression (1 + 2.5 is float). Checking is given an expected type and pushes it inward (xs: list[int] = [] types the empty list as list[int]). Alone, [] has no type; with an expected type it does.
12Is the type system Hindley–Milner?
No. The compiler uses bidirectional local inference with one fixed type per variable. The converter for untyped code uses a whole-program fixpoint over a type lattice (join evidence until nothing changes), which is simpler than HM unification and gives up on conflicts instead of generalising.
13Why Pratt parsing?
Expressions have many precedence levels. A Pratt parser uses one loop and a binding-power table, so adding an operator is one line, and right-associativity (**) is a small tweak. A cascade of grammar functions would need one function per level.
14What is the Semantic Fidelity Report?
A list, produced by the compiler, of every place where C++ could behave differently from Python: position, class (D1 to D14), what could differ, what we did, and a severity (exact, guarded, divergent). On our corpus it has 1280 notes: 42.6% exact, 56.7% guarded, 0.7% divergent. We did not find a surveyed tool whose documentation describes a per-site report like this.
15What is PIR?
The typed tree after lowering. It uses the same node classes, but every implicit conversion (bool to int to float) is an explicit Coerce node and every risky site carries a fidelity note, so the emitter never has to infer anything.
16What does guard elision do, and is it sound?
Every int + - * is a checked call by default. Interval analysis computes a range for each integer expression; where the range provably fits, it marks the operation unguarded. It is sound by construction: unknown means keep the check, and loop-carried variables are treated as unknown. Measured gain on our kernels is real but modest, and it does nothing for accumulators.
17What does “verified” versus “guarded” mean?
Both mean every replayed call matched. “Guarded” also means the function contains sites we cannot prove safe, such as integer addition that could overflow int64, which raises instead of wrapping. “Verified” has none of those.
18Why a 1.1x threshold?
Compiling a function does not make it faster if copying its arguments across the boundary costs more than it saves. We measure each function and keep it only if the median speedup is at least 1.1x. Below that it is “declined” and the number is shown.
19What if the traced run does not cover a code path?
Then that path is untested. Replay only checks the calls the program made (plus generated inputs, labelled). That is why the entry command should exercise the hot code, and why we call it differential testing.
20Does it change my code?
Not your folder. It works on a copy. In the copy, each accepted function gets one decorator line and the original body stays, so it is reversible, and if the compiled module cannot run, the Python body does.
21Is it safe to run on unknown code?
No. Tracing and replay execute your project. The server listens only on 127.0.0.1 and rejects foreign Host headers, but you should only run it on code you trust.
22How does it find the hot functions?
It runs your entry command with a tracer that uses sys.monitoring on Python 3.12 or later (sys.setprofile before that) and records calls and time per function. The ranker combines time share, eligibility and a predicted marshalling cost.
23How does type inference work without an LLM?
Four steps: observe runtime types by running the program once; collect evidence from assignments, calls and returns into a lattice until nothing changes; for parameters nobody calls, try plausible type combinations; then let the real type checker accept or reject the whole result. If anything is ambiguous, such as int on some paths and float on others, it refuses.
24Did you use AI to build this?
Yes, and the repository says so: Claude (Opus 5.5 and Sonnet 5.5) and GitHub Copilot appear as co-authors on 99 of 143 commits, including the dictionary library. The product itself does not need an LLM to run. We are responsible for what we submit, and you should be able to explain any file you claim.
25What does “the compiler is the judge” mean?
The scanner does not keep a list of supported features. It extracts each function into a standalone module and runs the real parser and type checker on it. If it passes, the function is eligible. So when the compiler gains a feature, the scanner needs no change.
26What are the time complexities?
Lexing, parsing, type checking, lowering, interval analysis and emission are linear in the size of the unit. Inference iterates passes of linear cost until the lattice stops changing (it has finite height). The search tries at most 400 type assignments, each a full check. Build time is dominated by g++.
27Why is the end-to-end speedup smaller than the per-function speedup?
Amdahl’s law: only the converted functions get faster. On TextLab, functions are 4x to 44x faster but the whole program is 2.6x, because the rest still runs in Python and the program has other costs.
28What are the known bugs?
Honest list: the snippet coin_change is refused (21 of 22 snippets); the grammar file is the v0.1 core and has not been regenerated for the later language; some fidelity-note text is stale (D8 still mentions setjmp); and STATUS.md lists three stress-harness cases found earlier that we did not re-investigate.
29What would you do with another month?
Bignum promotion and UTF-8 strings, zero-copy buffers, type-specialised versions so int-or-float functions convert, a VS Code extension, and a larger independent corpus with a comparison against Cython, mypyc and Codon so the novelty claim could become a paper.
30Can I see it work?
Yes. Section 10 is the demo script: it runs the app on a small public repository, shows the pipeline, one diff, and one function it correctly leaves alone, in under three minutes.
